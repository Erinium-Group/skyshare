[2026-08-22] | Le brief de la Tâche 5 utilisait des fonctions libres `crypto_box::seal(&mut rng, &pk, msg)` / `crypto_box::seal_open(&secret, scelle)`. La version 0.9.1 réellement résolue par le workspace n'expose pas ces fonctions : le module « seal » n'y ajoute que `SEALBYTES` et un helper de nonce privé, et l'API publique équivalente est portée par des méthodes — `PublicKey::seal(&self, &mut rng, msg)` et `SecretKey::unseal(&self, scelle)`. Le code du brief a donc échoué à la compilation avec `crypto_box::seal` introuvable, une erreur distincte de celle anticipée par le brief (RED attendu sur `Identity` manquant, obtenu à la place sur l'implémentation). | Quand le code d'un brief cite une API de crate par nom de fonction/méthode, si la compilation échoue *après* avoir écrit l'implémentation suggérée (pas seulement au stade RED des tests), lire le source réellement vendu dans `~/.cargo/registry/src/.../<crate>-<version>/` (via `Cargo.lock` pour la version exacte) plutôt que de deviner une signature proche. Le surcoût constaté (`SEALBYTES = 32 + 16 = 48`) confirme que seule la façade d'appel a changé, pas le format binaire — donc les tests de comportement (dont `surcout_borne`) restent inchangés.

[2026-08-22] | J'ai conclu trop vite que la détection NVENC était BLOCKED faute du NVIDIA Video Codec SDK (nvEncodeAPI.lib/nvcuvid.lib absents). Le SDK ne fournit qu'une bibliothèque d'import *statique* — une commodité de lien, pas le code. `nvEncodeAPICreateInstance` est en réalité livrée dans `nvEncodeAPI64.dll`, installée avec le driver GPU lui-même (vérifié présent dans `C:\Windows\System32`). J'aurais dû vérifier ça avant d'escalader. | Avant de rapporter un blocage « bibliothèque native absente » : vérifier si le binaire/DLL runtime existe déjà sur la machine (souvent livré par le driver/runtime, pas par le SDK de dev) et si un chargement dynamique (`libloading` + `GetProcAddress`, comme FFmpeg/OBS pour NVENC) est possible avant de conclure qu'une installation tierce est nécessaire. Piège additionnel sur MSVC : même quand aucun appel réel n'emprunte le chemin qui référence les symboles liés statiquement d'une crate (ex. `nvidia-video-codec-sdk::safe::Encoder`, jamais utilisé ici), le lien `debug` peut encore exiger ces symboles à cause d'un `lazy_static!`/`Once` interne à la crate dont l'initialiseur est toujours compilé — `/OPT:REF` ne le supprime pas en debug (seul `--release`, opt-level 3 sur tout le graphe, y arrive, et pas de façon fiable si limité à une seule dépendance). Fix robuste et indépendant du profil : fournir soi-même une définition `#[no_mangle] extern "C" fn` (corps `unreachable!()`) pour les symboles jamais réellement appelés — satisfait le linker sans jamais s'exécuter.
